## Changes and limits

- `firmware/src/ota_maintenance.cpp`: pinned ESP-IDF 4.4.7 dispatches default netif AP_STOP after the earlier registered application observer. Register the observer after the default handlers, so the acknowledgment now follows the default netif stop. If stop, acknowledgment, or deinit fails, keep driver dependencies alive and refuse reactivation until reboot, with HTTP closed and BLE restored. Track successful AP start so earlier startup failures do not wait for a nonexistent AP_STOP. Unregister/delete errors also block reactivation. The 4 KiB cleanup worker now parks and consumes a loop notification instead of publishing completion and self-deleting; IDF defers self-deletion to an idle task and the old static stack/TCB was reused by a later cycle. No observed crash was attributed to this reuse. Added a cumulative HTTP task watermark after real readback and AP_STOP event-task watermark in diagnostic builds; budget builds also give equivalent 5/60/300 s quiet heap/task samples without the ledger.
- Do not call this a vendor timer fix: `esp_wifi_stop`/AP_STOP/deinit previously succeeded. Linked Wi-Fi disassembly places the type-4 warning at a late dispatch guard; linked legacy ETS drops the handle even when armed `esp_timer_delete` refuses it. This can retain a timer; the observed refusal does not prove that it was the warning's timer or quantify retained bytes. No evidence establishes app use-after-free or an unbounded leak. Do not patch, silence or disarm the opaque vendor timer without identified ownership. [Historical endurance](ota-lifecycle-endurance.md) lost 4,056 current INTERNAL bytes over 50 recorded cycles and recovered only 128 after 300 s; it retained a real login transport failure. A one-time lwIP warm-up, delayed sockets, BLE allocations, timer retention and free-block topology remain distinguishable hypotheses, not conclusions.
- `tools/ota_deploy.py`, `scripts/ota_tool.py`: live writes require a frozen signed package pinned by digest, and a matching exact running build/slot/hash plus `VALID`/confirmed/healthy. The client reads bounded bytes once and uploads the same verified bytes. Verify exact staged size and build with the latest nonce before sending a single install POST. Record upload acknowledgment, verified staging, install response, expected-image boot and confirmed health distinctly; after a missing/malformed install reply observe reboot without replay. Persist only validated known device fields. Restore WLAN and Ethernet on all paths, and don't treat HTTP close acknowledgment as observed teardown. Live build-and-deploy and live USB activation are no longer allowed. No trust/key, partition, memory floor, scoring, pin, geometry, brightness or power changes.
