The network/session consumed **58,384** bytes at shutdown start and returned **58,080** to the immediate-closed sample. The **304-byte** difference is not a settled comparison or an additive leak estimate. The earlier same-stage series lost **4,056** bytes; only **128** returned after 300 s. That is persistent loss of free capacity over the measured window, not a proven unbounded leak. A 39,756-byte historical minimum is not an upload minimum. No new MCU before/after numbers exist for either signed diagnostic image.

Pinned framework: PlatformIO espressif32 6.13.0, Arduino-ESP32 2.0.17, ESP-IDF 4.4.7. Reviewed the installed ELF, exact linked diagnostic ELF and pinned sources/archives (hashes in session). Specifically:

- **Timer/Wi-Fi:** the installed `ieee80211_timer_process` warning is a guard after API-lock acquisition when Wi-Fi is no longer initialized; the warning branch itself has no timed wait. The physical stop, AP_STOP and deinit all succeeded. Type 4 is a vendor dispatch ID, not the return code of public deinit. `ets_timer_done` discards `esp_timer_delete`'s result and clears its handle; a delete of an armed timer returns `ESP_ERR_INVALID_STATE` without freeing it. Conversely `ESP_OK` queues a delete on the timer task; it does not immediately free the allocation or rule out an already queued Wi-Fi dispatch. Only a failed handle/owner surviving the matching settled checkpoints (with count/byte reconciliation) supports the orphan hypothesis. Warning without rejection or retained timer allocations supports late dispatch independent of the drift. No SDK teardown change is justified yet.
- **Event and HTTP:** application ownership is per window: custom event registration, default AP driver/netif and (if created here) default loop. Unregister and destroy release handler contexts/driver storage; loop deletion frees queued event storage. Application AP_STOP is an acknowledgement, not proof every handler has run at that instant. `httpd_stop` waits for STOPPED, then deletes server/session/URI resources; task storage can settle after task exit. Compare stage releases and settled survivors, not the instant the stop call returns. No matched persistent application-owned allocation identified.
- **TCP/IP:** `esp_netif_init` initializes lwIP/TCPIP infrastructure once. IDF 4.4.7 explicitly does not support lwIP deinit. This explains a possible one-time baseline step, not a continuing cycle-index slope. Socket close is not necessarily PCB free: this pinned lwIP removes TIME_WAIT after twice its 60 s MSL, so 60 s is an intermediate checkpoint and 300 s the decisive comparison for ordinary TIME_WAIT. Look for TCP/lwIP owners that disappear by 300 s vs. survivors after it.
- **BLE:** the controller, host, GATT service and queue are boot-lived; authorization/disconnect and advertising stop/restart do not deinit them. Arduino's `BLEAdvertising::start` frees its temporary UUID array on the normal path (early GAP config errors can skip that release; no such error was established in the old capture). A BLE-only cycle isolates connect/subscription/advertising traffic from all Wi-Fi work. Do not change BLE configuration or callbacks based on this possibility alone.
- **Allocator:** stable largest block is evidence against worsening *maximum*-block fragmentation at those checkpoints, not evidence against fragmentation in smaller pools. Compare allocated blocks, allocated bytes, free-block topology and surviving owners. Bin/poison/alignment overhead means ledger request sizes need not exactly equal allocator deltas. Free heap loss with stable live allocation metrics calls for analyzing free-block topology or missed coverage, not declaring a leak.

## Verified fix and diagnostic scope

The actual status projection now gives `{received:0,total:0,stagedBuild:""}` in Session/Window/Closed, even if the last upload was interrupted. Receiving exposes progress but not a staged build; Staged/Installing preserves the verified build and size. Authorization, nonce and transfer eligibility are unchanged. A regression exercising real `Policy`/`Transfer` and fake `Sink` first failed `Expected 0 Was 24`, then passed for interrupted transfer and fresh login. The historical assertion was made before saving any sanitized fields, so stale progress is a verified defect, **not proof of which field failed in that particular uncaptured response**. Future runners must save only phase/received/total/stagedBuild/heap before asserting; do not record token, nonce or raw auth headers.

- `ota_ownership` (`agent-life2-own`): bounded 256-entry allocation ledger, starting after BLE service startup and before first OTA networking. Wraps the allocating/freeing `multi_heap_*` calls actually linked from the pinned caps allocator (aligned wrap supplied but the aligned path was stripped). Emits addresses, requested sizes and up to four caller PCs only at quiet 5/60/300 s checkpoints, plus app handler/netif/loop cleanup boundaries, task counts, AP_STOP event-task margin and latest rejected timer handle/caller. No heap allocation, output or allocator lock nesting inside the wrappers. Normal flows never consult diagnostic state for admission. Attribute across snapshots within the same boot; use the matching ELF with `xtensa-esp32-elf-addr2line -f -C -e firmware.elf` for PCs. A dropped/skipped record, missing PC, duplicate address or changed revision/count across `OTA OWN begin/end` means incomplete evidence; never use it to rule out an owner. Skips include unsafe ISR/cache-disabled contexts, and interception cannot see private pools, allocations before the trace, or calls bypassing the link seam. The extra static **6,224 B** vs `ota` can change heap placement/admission. Use this profile for ownership, not to certify upload reserves.
- `ota_budget` (`agent-life2-budget`): allocation-boundary samples of current INTERNAL and INTERNAL/8-bit free during named intervals; largest INTERNAL/8-bit block at bounded checkpoints only. Start/end stack watermark (in **bytes**) is of the calling task. Upload markers cover genuine signature, first and later erase/write, SDK end and extent verification, readback, and completion; the loop covers selecting boot, candidate validation/startup and confirmation. No ownership table; **40 B** extra static vs `ota`. Samples are not atomic, and misses/in-flight allocations or SDK-internal temporary allocation/free pairs can hide a sharper minimum. Sampled peak demand = start free minus the observed low, not a guaranteed worst-case reservation. Treat `skipped` as a coverage limit and correlate with boot-wide SDK minima; use the minimum *sampled* largest block, not historical minimum free heap, for the contiguous margin.

### Stack/heap envelope

HTTP upload and readback run on the **same 8,192 B** task; readback does not allocate another task. In the budget ELF `uploadHandler` takes 1,472 B and nested readback 1,104 B, so **2,576 B** is a frame-only lower bound on stack consumption in readback. `finish` takes 336 B and nested `esp_ota_end` a further 304 B before nested verification calls. Candidate boot validation takes 1,488 B on the separate 8,192 B Arduino loop. SDK/HTTP parent frames, ECDSA (inlined app adapter with deep mbedTLS calls), transport/formatting, spill/interrupt effects and measurement code are not covered by these numbers. A reserved stack is not a measured high-water mark. The only physical task margin from the latest capture is **2,300 B of the 4,096 B cleanup stack**, not HTTP/loop.

Sequential write uses a 44-byte OTA handle record (before allocator overhead), incremental erase/write and 1 KiB stream and independent readback buffers, not a 1.6 MB in-RAM image or a full-slot pre-erase at begin. Actual flash scratch, mmap/image verification, TCP buffers and candidate startup/confirmation still need measurement. Earlier no-erase physical ECDSA probes had roughly 57.3 KB current INTERNAL and at least 28,660 B largest INTERNAL/8-bit at signature checkpoints; they do not measure nested crypto peak. No threshold changes: startup 100,000 B, operation 49,152 B plus 4,096 B contiguous at write-related gates, emergency 32,768 B. Do not infer those floors are sufficient for a complete transaction from the old samples or frame arithmetic. Require zero allocation/admission/stack/watchdog failures, intact readback and confirmed boot, and report post-operation HTTP and loop minimum margins and worst observed heap/contiguous margins before approving or sizing a release. Treat any margin below 512 B stack as an immediate bench stop, not a new firmware floor or a blanket claim that 512 B proves sufficient.

## Finite, owner-gated hardware plan

**No matching spare was confirmed available.** Prefer an existing matching ESP32-WROOM-32 with the same flash, bootloader, DMA reservation, BLE/Wi-Fi coexistence and pinned software. Do not require a purchase. Owner authorization and identity/USB recovery checks precede all physical actions below.

1. On a spare, or on Court1 **only after separate authorization** for a USB app-only diagnostic change in `ota_0`, use `agent-life2-own`. On Court1: no match in progress, allow score reset, isolate USB-only (no external 5 V), verify chip/slot and keep USB ROM recovery accessible. Both existing full 4 MB backups were freshly file-hash verified (`181dcc684f706a7021cd7e39c31f2ccb226ae050b35056bbd4de8243a7a76b2f`); before any authorized write, take and independently verify a fresh read against expected regions and confirm saved original fallback and known `agent-wpa2` app are recoverable. If identity, backups or USB recovery differ, stop. Write only the running app region if later explicitly allowed, verify it and verify that `ota_1`, OTA data, NVS, bootloader and table are unchanged. Do not use a PlatformIO generic upload, whole-device erase, or OTA to install this diagnostic on Court1. If recovery is needed, stop for a separately authorized, verified app-only restore over USB; retain full backups for exceptional recovery, not routine restore. A file backup is not permission to overwrite the on-device fallback.
2. Start raw private serial capture before boot. Let the boot AP expire with no station; wait 300 s closed for a warmed reference. Run **one BLE-only** subscribe/read/disconnect with no scoring command or authorization proof; **one AP-only** authorized reactivation without a station, letting the window expire; **one authenticated no-write** activation/login/status/close over pinned WPA/DHCP/HTTP. Restore WLAN and observe Ethernet. Wait for all 5/60/300 s samples after each intervention, with no BLE traffic in the quiet windows. Record build/uptime and sanitized status before asserting. Diff matching stage counts/owners, match rejected handle to its surviving trace and timestamp the raw type-4/5 warning. Stop after those arms; repeat just the implicated arm once if needed to distinguish persistent step vs. recurring growth. Abort on identity mismatch, admission/cleanup failure, reset/panic/watchdog, score change or insufficient diagnostic coverage. No broad endurance loop.
3. Full signed transfer/readback/selection/trial is **bench-only** and requires separate permission and an expendable inactive slot. Run the `ota_budget` profile with a distinguishable signed, budget-instrumented candidate under the same measured warm state. Start capture before the request; compare signature and body interval minima and task watermarks through first and later erase/write, SDK end, extent, readback, boot selection and candidate startup/confirmation. The HTTP watermark includes earlier request parsing, but allocator interval minima start at signature, not header receipt. Reconnect and verify health. Verify exact hash/slot, `VALID`/healthy, and WLAN restoration. Separately test one deliberately failed trial/rollback on the spare only. **Do not run this step on Court1 under the current fallback-preservation constraint:** writing a valid upload to inactive `ota_1` would erase the original fallback even with no install POST. If no spare is available, step 2 can still attribute memory without touching `ota_1`; full-path runtime budget remains unverified. No live deployment is proposed.
